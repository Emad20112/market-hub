# ADR-002 — خروج Business Logic من PostgreSQL

**الحالة:** معتمد | **التاريخ:** 2026-11-07
**المصدر:** قرار المالك + `docs/ARCHITECTURE_REVIEW_V2.md` + تصنيف
`supabase/arch-fn-classification.md` (296 دالة).

## السياق
296 دالة SQL تحمل منطق أعمال ERP (مبيعات، محاسبة، مخزون…) داخل ترحيلات:
صيانة واختبار وتتبع أخطاء شبه مستحيلين، ومنطق مقسّم بلا حدود واضحة.

## القرار
Backend هو **المصدر الوحيد** لقواعد العمل والتنسيق ودورة العمل. قاعدة البيانات =
طبقة بيانات وحماية فقط: جداول، علاقات، فهارس، قيود، Enums، Views للقراءة الثقيلة،
RLS، ومشغلات **سلامة بيانات** فقط (لا workflows).

## التصنيف المعتمد
| القرار | العدد | الأساس |
|---|---|---|
| تنتقل للـ Backend | 172 (132 مباشرة + 40 بإعادة تصميم) | منطق أعمال/workflows |
| تبقى في القاعدة | 66 | مشغلات سلامة + دوال سياسات RLS + تابعة حصرية لها |
| مرشحة للحذف | 35 (مؤكدة 30، وبؤال 5: handle_new_user, rpc_allowlist, payment_method_catalog_view, get_batch_settings, sync_apply_operation) | لا مستدعين (بعد تدقيق الاستدعاء الديناميكي) |

## لماذا تبقى الـ 66 (أسباب تقنية، لا تفضيل)
1. **دوال المشغلات (~30):** ضمانات تكامل تنطبق على أي مسار كتابة مهما كان مصدره
   (خادم، إصلاح يدوي، عملاء مستقبليون). لا بديل خارج محرك القاعدة.
2. **دوال RLS (~20):** RLS لا يمكن أن يعمل خارج محرك القاعدة (`has_role`, `is_staff`…).
3. **تابعة حصرية (~16):** تستدعيها (1)/(2) داخلها — نقلها يعني تكرارًا أو كسر ضمانات.
   تُراجع دوريًا: كل دالة تنفصل عن المشغلات بعد إعادة التصميم تنتقل هي الأخرى.

## العيوب المقبولة
- نافذة انتقال طويلة (dual-run) — تُدار بحدود ESLint تدريجية (ADR-007 جودة).
- كل عملة/تقريب/ترتيب حسابي ينتقل من numeric/SQL إلى TS — تُقارن النتائج قبل الحذف
  (اختبارات تكافؤ، ADR-006 اختبارات).

## القواعد الملزمة
1. يُمنع إنشاء دوال SQL لمنطق أعمال جديد — الاستثناء الوحيد: مشغل سلامة بيانات،
   يُوثق في `DECISIONS` مع سبب تقني ("لا يمكن تنفيذه خارج القاعدة" ≠ "أفضل هناك").
2. حذف دالة SQL بعد نقلها: فقط بعد إثبات صفر استدعاء (grep شامل + تدقيق حي) + توثيق.
3. الترقيم يُمنع أي كتابة مباشرة من الواجهة على PostgREST (تفعيل RLS write-deny).

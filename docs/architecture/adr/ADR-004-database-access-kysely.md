# ADR-004 — طبقة الوصول إلى قاعدة البيانات: Kysely على pg

**الحالة:** معتمد | **التاريخ:** 2026-11-07 | **من:** 3 بدائل

## البدائل المفحوصة
| المعيار | **Kysely** (اختيارنا) | Drizzle ORM | pg خام |
|---|---|---|---|
| Type Safety | ✅ قوي، مع `kysely-codegen` مولّد من القاعدة نفسها | ✅ لكن يفرض تعريف schema ثانية بالكود (تكرار لمخطط Supabase) | ❌ |
| الترقيم/المعاملات | ✅ `db.transaction()` + `withTransaction` مخصصة | ✅ | ✅ يدوي وعرضة |
| SQL خام عند الحاجة (تقارير/أقفال) | ✅ `sql` template بلا احتكاك | ✅ | ✅ |
| الترقيم التدريجي من دوال SQL قائمة | ✅ الاستعلامات تُترجم واحدة واحدة بمطابقة مناظرة | ⚠ DSL جديد يضيف جهدًا بلا فائدة هنا | ✅ لكن بلا حماية أنواع |
| الصيانة | ✅ API صغير مستقر | ✅ | ❌ سلاسل نصية هشة |
| الأداء | ✅ إرسال استعلام واحد مُعامَل | ✅ | ✅ |

## القرار
- **Kysely + `pg`** (حزمة `kysely`، `pg` موجودة بالفعل في المشروع) عبر Pool.
- الأنواع مولدة: `kysely-codegen` من مخطط Supabase المحلي (`npm run db:types`-style
  سكربت جديد) إلى `src/server/shared/db/schema.d.ts` — مصدر وحيد لا تكرار يدوي.
- **Supabase-js يبقى** فقط لـ: Auth (جلسات)، Storage، والقراءات REST البسيطة
  أثناء الانتقال. **يُمنع** `supabase.rpc` في الواجهة (قاعدة ESLint)، ويُسمح به
  مؤقتًا داخل `infrastructure/` فقط حتى استبداله.
- كل كتابة Business عبر Kysely/pg؛ PostgREST write على جداول الأعمال يُمنع بسياسات
  RLS write-deny بعد اكتمال كل مجال.

## القواعد
1. لا استعلام SQL خارج `infrastructure/` (قاعدة ESLint).
2. كل جدول له Repository واحد بمالك مجال واحد.
3. الاستعلامات الخام للتقارير الثقيلة تُكتب كملفات SQL مُعامَلة داخل repository
   وتُختبر — لا بناء نصوص بـ interpolation.

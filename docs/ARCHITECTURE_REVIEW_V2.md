## 1. تحليل تأثير إزالة Business Logic من قاعدة البيانات

### ما نكسبه
- منطق قابل للاختبار بوحدات TS سريعة بلا قاعدة حية.
- تتبع أخطاء وتنقيح (debugger) وأدوات حديثة بدل SQL مخفي داخل ترحيلات.
- إعادة استخدام وتركيب منطق بين المجالات دون دوال SQL متراصة.
- قاعدة بيانات صغيرة: جداول + قيود + فهارس، سهلة المراجعة والفهم.

### التكاليف والمخاطر (يجب إدارتها صراحة)
1. **الذرّية:** العمليات المالية متعددة الجداول (قيد + مخزون + رصيد عميل) كانت ذرّية لأنها داخل دالة واحدة. الحل: معاملات صريحة عبر اتصال pg مباشر من الخادم (`BEGIN … COMMIT`) — نفس الضمان، بأداة مختلفة (§6).
2. **RLS:** منطق الصلاحيات المدمج في دوال RPC ينتقل لطبقة Authorization في Backend، مع إبقاء RLS في القاعدة **كدفاع ثانٍ** (لا يُحذف) — قاعدة تُكتب عبر اتصال الخادم تحمل هوية المستخدم فتظل RLS مطبقة (§8).
3. **الأداء:** القراءات التجميعية الضخمة (كشوف، تقارير) تبقى استعلامات SQL — لكن تُنفَّذ من Backend عبر Repositories بدل دوال RPC؛ نفس خطة الاستعلام، نفس الأداء تقريبًا، مع إمكانية التحسين لاحقًا.
4. **حجم العمل:** ~172 دالة تنتقل (132 مباشرة + 40 بإعادة تصميم). هذا مشروع كبير بالتدريج — تفصيله في §11.
5. **نافذة الانتقال:** RPC القديمة وBackend الجديد يعملان معًا (dual-run) حتى اكتمال استبدال كل مجال، ثم تُحذف الدوال من القاعدة.

## 2. جرد وتصنيف الدوال (النتيجة الفعلية)

من `arch-fn-classification.md` (توليد آلي + تدقيق يدوي):

| القرار | العدد | المعيار |
|---|---|---|
| **تبقى في القاعدة** | 66 | مشغلات سلامة بيانات، دوال سياسات RLS، ودوال يستدعيها هؤلاء حصريًا |
| **تنتقل إلى Backend مباشرة** | 132 | منطق قابل للترجمة: CRUD، تحقق، تسلسل أرقام، حسابات |
| **تنتقل مع إعادة تصميم** | 40 | Workflows متعددة الجداول (create_sale, post_sales_invoice, post_stock_delta…) — تُفكك إلى Use Cases داخل معاملات واحدة |
| **مرشحة للحذف** | 35 | لا مستدعين في SQL ولا في الواجهة (بعد تدقيق الاستدعاء الديناميكي) |

**تصحيحات التدقيق اليدوي (مهمة):**
- المستدعاة ديناميكيًا عبر `(supabase.rpc as any)` فانتقلت من "ميتة" إلى "تنتقل":
  `record_customer_payment_splits`, `record_customer_advance_payment`, `create_milling_service_document_multi_priced`.
- `post_stock_settlement` ميتة فعلًا (ذكر في تعليقات فقط؛ الشاشة تستخدم `post_stock_adjustment`).
- `handle_new_user` لا يوجد لها مشغل في خط الأساس (`on auth.users` = 0) — لكنها قد تكون موصولة كـ Auth Hook في المشروع السحابي: **تُدقق على القاعدة الحية قبل الحذف**.
- `rpc_allowlist` غير مستدعاة في خط الأساس — أثر تاريخي؛ حذف مؤجل بعد تدقيق حي.
- قائمة الحذف الكاملة مع الأسباب في ملف التصنيف؛ **لا حذف إلا بعد grep نهائي + تدقيق على قاعدة حية**.

### لماذا تبقى الـ 66؟ (أسباب تقنية صريحة، لا تفضيل)
1. **دوال المشغلات (~30):** `tg_set_updated_at`, `tg_expense_lines_sync_total`, `tg_customer_ledger_sync_balance`, `trg_purchase_invoice_to_supplier_ledger`… — سلامة بيانات يجب أن تنطبق على أي مسار كتابة (خادم، إصلاح يدوي، مستقبلًا عملاء آخرون). لا بديل خارج القاعدة.
2. **دوال سياسات RLS (~20):** `has_role`, `is_staff`, `expense_role_rank`, `can_read_finance`… — RLS لا يمكن أن يعيش خارج محرك القاعدة. تظل هي المصدر حتى مع Authorization في Backend (دفاعان، طبقتان مستقلتان).
3. **تُستهلك حصريًا من (1) و(2) (~16):** `recalculate_customer_balance`, `item_effective_policy`, `payment_method_resolve_id`… — تحسب داخل مشغلات/سياسات؛ نقلها يعني تكرار منطق أو كسر ضمانات القاعدة. تُراجع لاحقًا: كل ما ينفصل عن المشغلات بعد إعادة التصميم ينتقل هو الآخر.

**القرار: الخيار 1 — Backend داخلي في TanStack Start** بوحدة بنية سداسية (Hexagonal) تُحصر منطق الأعمال في طبقات لا تعرف إطار العمل، فأي استخراج مستقبلي إلى خدمة مستقلة يصبح نقل طبقات لا إعادة كتابة. الخيار 2 يظل بديلًا مشروعًا إذا نشأ عملاء متعددون/قنوات برمجية خارجية — والتكلفة آنئذٍ مدفوعة مسبقًا بالتصميم.

## 4. الطبقات (Layered + Hexagonal داخل النطاقات)

```
        Transport (server functions)  — رقيقة: تحقق مدخل + استدعاء Application
                     ↓
        Application (Use Cases)       — تنسيق العملية، حدود المعاملة، صلاحيات الدخول
                     ↓
        Domain (قواعد العمل النقية)   — حسابات، قواعد، سياسات — بلا I/O
                     ↓
        Infrastructure (Repositories) — SQL/Supabase فقط هنا
```
- **اعتماد الاتجاه واحد:** Transport→Application→Domain، وApplication/Domain تستخدم Infrastructure عبر واجهات (Ports) معرفة في Domain/Application.
- **Domain نقية 100%:** كل قاعدة عمل (حدود ائتمان، حالات المستند، حساب الضريبة) قابلة للاختبار بلا قاعدة بيانات.

## 5. هيكل المجلدات

```
src/
  server/
    api/<domain>/         # server functions (Transport) — ملف لكل عملية: create-sale.ts
    domains/<domain>/
      application/        # use-cases: create-sale.usecase.ts
      domain/             # entities, rules, domain-errors: sale.ts, credit-limit.rule.ts
      infrastructure/     # repositories: sale.repository.ts (pg/Supabase)
      contracts/          # types.ts, dto.ts, mappers/
      validators/         # zod + قواعد مدخل
      index.ts            # واجهة المجال العامة
    shared/
      db/                 # pool.ts, transaction.ts (Unit of Work), query-builder
      auth/               # authorization.ts, session-context.ts
      errors/             # DomainError hierarchy, mapper من أخطاء PG
      time/               # business-time (مقابل دوال business_*)
      numbering/          # توليد أرقام المستندات (قفل صف + زيادة)
      testing/            # أدوات اختبار بمعاملة تُرجَع rollback
  routes/                 # تستدعي server functions فقط — لا RPC
```

## 6. إدارة المعاملات (Transactions)
- `shared/db/transaction.ts`: `withTransaction(async (tx) => …)` — اتصال من Pool، `BEGIN`، تمرير `tx` للـ Repositories، `COMMIT/Rollback`. لا Repository يقبل اتصالًا خارجيًا ضمن معاملة دون `tx`.
- Unit of Work لكل Use Case: كل كتابات العملية (قيد محاسبي + حركة مخزون + رصيد) داخل **معاملة واحدة** — مكافئ دقيق لما كانت تفعله الدالة الواحدة.
- **قفل التزامن:** ما كان يعتمد على `SELECT … FOR UPDATE`/advisory locks داخل الدوال (مثل `customer_balance_lock`) يُترجم كما هو داخل المعاملة — لا تغيير في دلالات القفل.
- توليد أرقام المستندات: نفس آلية sequence/قفل الصف القائمة، عبر Repository.

## 7. الأخطاء (Error Handling)
- `DomainError` أساس + فئات: `ValidationError`, `BusinessRuleError`, `AuthorizationError`, `NotFound`، وأخطاء المجالات (`SalesError`, `AccountingError`…).
- `shared/errors/pg-mapper.ts`: تحويل أكواد PostgreSQL (23505, P0001…) إلى `DomainError` بمحتوى عربي/إنجليزي — يستبدل `translateRpcError` الموجود تدريجيًا.
- Transport يرجع `{ code, message, details }` موحدًا لكل الواجهة؛ لا try/catch خام في الشاشات.

## 8. الصلاحيات (Authorization) + الوصول للقاعدة
- **طبقة Authorization في Backend:** `authorize(session, capability, resource)` لكل Use Case — تنقل دلالات دوال الصلاحيات (`expense_assert_capability`, `can_operate_milling`…) إلى TS.
- **RLS يبقى في القاعدة** كدفاع ثانٍ: اتصال الخادم يضبط `SET LOCAL role authenticated; SET LOCAL request.jwt.claims` لكل معاملة بهوية المستخدم، فتبقى سياسات القاعدة مطبقة على كل استعلام. النتيجة: لو سقط منطق الصلاحيات في Backend، القاعدة ترفض.
- قناتان للوصول: **pg Pool** (كتابة/معاملات/تقارير) و**supabase-js** (قراءات REST البسيطة أثناء الانتقال، Auth/Storage). الاتجاه النهائي: pg لكل Business data.

## 9. استبدال استدعاءات RPC
- كل Route/Hook/Hook-like lib يستدعي **server function** التي تغلف Use Case.
- 3 مواضع استدعاء ديناميكي (`use-financial-posting`, `custody.ts`, `_app.payments.tsx`) تُستبدل باستدعاءات صريحة لكل عملية (إزالة الديناميكية عمدًا — هي مصدر غموض).
- `rpc_allowlist` وتواقيع الأمان المرتبطة بالـ RPC تُلغى مع آخر RPC (الواجهة لن تلمس PostgREST للكتابة).
- Offline sync engine: عمليات RPC في Outbox تتحول إلى أوامر server functions (يُعاد تصميمها في مرحلة مجالها).

## 10. الواجهة العامة الجديدة للنطاق
`src/server/domains/<domain>/index.ts` يصدّر Use Cases فقط. قاعدة ESLint للحظر (وضعها الحالي warn على `supabase.rpc` خارج `src/domains`) تُوسَّع لاحقًا: حظر `.rpc` نهائيًا خارج server، وحظر استيراد repositories من Transport/الشاشات — تشديد تدريجي موثق.

## 11. خطة الانتقال التدريجية (كل مرحلة تحافظ على النظام عاملًا)

**نمط كل مرحلة (Repeatable):**
1. بناء عقود المجال (types/validators) + Domain نقية + اختباراتها.
2. Repositories + Use Cases + معاملة + Authorization + اختبارات تكامل على قاعدة محلية.
3. Server functions + استبدال مواضع الاستدعاء في الواجهة (dual-run: ما لم يُستبدل يظل RPC).
4. مقارنة سلوكية (نتائج العملية قبل/بعد على بيانات اختبار) + lint + اختبارات المشروع.
5. **حذف دوال SQL للمجال** من ترحيل جديد (DROP FUNCTION) بعد إثبات صفر استدعاء، وتوثيق الحذف.
   (خط الأساس الجديد يبقى للقاعدة الجديدة؛ دوال قاعدة حية تُسقط بترحيل أمامي عند التحويل.)

## 12. ما يبقى في القاعدة نهائيًا (المستهدف)
جداول، علاقات، فهارس، قيود، أنواع، views القراءة الثقيلة عند الحاجة، سياسات RLS، مشغلات سلامة بيانات (~66 دالة الآن، وتتقلص بمراجعات لاحقة كلما أمكن إزاحة منطق للخارج)، ولا أي RPC منطق أعمال.

### خطة الانتقال لكل نطاق (نمط موحد يعاد لكل مجال من §11)
لكل مجال: قراءة دواله وتوثيق سلوكه الملاحظ (حالات، رسائل خطأ، ترتيب عمليات)
→ عقود + Domain نقية + اختبارات → Repositories + Use Cases + `authorize` +
معاملات → **اختبار تكافؤ** (القديمة والجديدة على نفس بيانات اختبار، مقارنة رقمية
كاملة) → server functions + استبدال مواضع الاستدعاء تدريجيًا (dual-run) →
إثبات صفر استخدام (grep شامل + تدقيق حي) → ترحيل `DROP FUNCTION` موثق.
